# 1.3.4 — vpprotocol 2.3.37.15 → 2.3.80.15 + vpbluetooth 1.18 → 1.20 (Android)

## Why

The Android binaries went in with the fork's initial commit (`ea32cb2`) and had
never moved, while upstream `HBandSDK/Android_Ble_SDK` shipped 43 protocol
versions ahead. Indexing both AARs put the gap at 542 → 775 `com.veepoo.*`
public classes (+236 added, 3 removed — all three obfuscated internals, so
nothing callable disappears); of the additions ~190 are obfuscated internals and
46 are new public model / listener / enum classes (live emotion / MET / HRV
detect, `EGsrUnit`, QX17 raw acquisition, sport status, GNSS, TCM, …).

This is a **binary bump plus drift repair only** — no new API is bridged.

## What changed

**`android/libs/vpprotocol-2.3.37.15.aar` → 2.3.80.15**
(`shasum ef524f66dc18d62cc0995daa1639a1001eaec60e`) and
**`android/libs/vpbluetooth-1.18.aar` → 1.20**
(`shasum 5b9beab792f6d6bc45c5f57c874e4453cacdad68`). Both are byte-identical to
the vendor's `android_sdk_source/jar_core/` copies at upstream `2856441e`.
`expo-module.config.json` `gradleAarProjects` paths follow the new filenames;
`android/build.gradle` needed nothing — its project refs are version-less names
(`:expo-veepoo-sdk$vpprotocol`).

**Listener drift measured, then fixed.** First compile against the new AARs:
**7 Kotlin errors, 2 distinct drifts**, every one verified with `javap` on the
new AAR before editing:

- `IOriginProgressListener` gained `onReadTimeout(int)` — inherited by
  `IOriginData3Listener` (origin/day-summary/all-data reads) and
  `ITemptureDataListener` (stored temperature). Six object expressions needed
  the override.
- `IPwdDataListener` gained `onConnectionConfirmTimeout()` — both
  `confirmDevicePwd` call sites (verifyPassword, verifyPasswordInternal) needed
  it.

Handlers settle promises at most once via `AtomicBoolean` guards; where a read
already has a timeout runnable or resolve-once helper, the new callback routes
through it. `verifyPassword` rejects with a new `CONNECTION_CONFIRM_TIMEOUT`
code, registered in `ALLOWED_NATIVE_REJECT_CODES`.

**Nothing is bridged.** The new public APIs get `notBridged` entries in a later
pass once there is an Android band on the bench to verify them against — green
Kotlin is still not working band support, and Android behaviour remains
unverified on hardware (iOS-only device verification, unchanged by this bump).
