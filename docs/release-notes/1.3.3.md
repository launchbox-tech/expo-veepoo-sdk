# 1.3.3 — VeepooBleSDK.framework 2.2.88.15 → 2.2.101.15 (iOS)

## Why

Our binary sat *between* vendor releases. It already carried `VPTCMTestDataModel`
and `VPGSRResultModel`, but not the manual emotion / MET / HRV models — checked
with `nm | grep '_OBJC_CLASS_$_'` against the binary, not against the docs, since
the framework `Info.plist` reports a useless `0.0.0.1` on both sides.

Upstream `HBandSDK/iOS_Ble_SDK` `a72fdefe` ships **2.2.101.15** (13,916,672 bytes
vs our 13,347,832), adding those models plus the spot-measurement methods that go
with them.

## What changed

**`ios/VeepooSDK/Frameworks/VeepooBleSDK.xcframework` → 2.2.101.15 (arm64).**
The device slice is byte-identical to the vendor's file
(`shasum 3a4d1b2d8ba74b15805288f14f6e636be47bd0ac`, compared against
`iOS_sdk_source/Framework/2.2.XX.15/VeepooBleSDK.framework/VeepooBleSDK` at
upstream `a72fdefe`); the simulator stub was regenerated
by `scripts/build-xcframeworks.sh` from the new `Headers/` and `module.modulemap`.
The other five frameworks are untouched.

**The bundled `Modules/VeepooBleSDK.swiftmodule` is removed again**, per the
standing rule from 1.3.1. 2.2.101.15 does now ship a `.swiftinterface` alongside
it, but the module is arm64-device-only and its entire surface is the ZK DFU
manager (`VPHZKDFUManager`, `OtaStatus`), which this module does not call. Keeping
it would put a device-only Swift module inside the simulator stub slice.

**Nothing is bridged.** This is a binary bump; the new APIs get `notBridged`
entries in `docs/vendor-sdk-snapshot/sdk-callback-coverage.json` and backlog rows in
`docs/vendor-api/vendor-parity-matrix.md` recording that
the omission is deliberate. Wiring `veepooSDK_emotionTest` / `metTest` /
`fatigueLevelTest` is separate work.

## The class list is a strict superset

283 defined ObjC classes → 297. **Zero lost.** Added:

```
VPDeviceSportWithGPSAltitudeHelp  VPManualGSRModel        VPMetTestManager
VPEmotionTestManager              VPManualHGBodyComModel  VPPhotoDialInfoCircle360_360_ZK_569X
VPFatigueLevelTestManager         VPManualHRVModel        VPReminderEventManager
VPManualEmotionModel              VPManualMetModel        VPReminderEventModel
VPManualFatigueLevelModel         VPManualStressModel
```

The header diff is additive too, and was checked for the failure mode the class
diff cannot see — a **reordered enum**, which would silently re-point the
connect/daily-read state machines:

- `VPManualTestDataType` gains `Stress` (1<<3), `Met` (1<<6), `HRV` (1<<7),
  `Emotion` (1<<10), `FatigueLevel` (1<<11), `GSR` (1<<12) — all in previously
  unused bit positions; every existing case keeps its value.
- `VPJH58MeasurementModeState` gains `ActiveTest = 0x04` at the end.
- New enums only otherwise (`VPTestMetState`, `VPTestEmotionState`,
  `VPTestFatigueLevelState`, `VPJH58ActiveMeasurementState`,
  `VPJH58ActiveMeasurementResultState`, `VPReminderEventType`,
  `VPHealthLightStatusType`).
- `VPDeviceConnectState` is unchanged.

No selector was removed: 365 first-part selectors across the old headers, all 365
still present, 384 now.

New methods on `VPPeripheralBaseManage`: `veepooSDK_emotionTest`, `metTest`,
`fatigueLevelTest`, `readIMEIInfo`, `listenReminderEventReport`,
`readHistoricalDataReminderEvents`, `triggerReminderEvent`,
`ReadHealthLightStatus`/`SetHealthLightStatus`/`ListenHealthLightStatus`,
`PowerOffDevice`, `SendExitUpdateFirmCommand`,
`JH58ActiveTestPPGAndAcceleration(Report)`.

## Verification

- Pod compiles clean on `-sdk iphoneos` (`RayuSTG.xcworkspace` scheme
  `VeepooSDK`, clean derived data): **BUILD SUCCEEDED**, 0 errors, 63 Swift
  compile actions. That is a `libtool -static` archive, so it proves the 53
  source files type-check against the new headers and nothing more.
- Link verified separately, because compile is not link: every `VP*` symbol
  `libVeepooSDK.a` leaves undefined (34) is defined by the new binary (437) —
  `comm` returns empty. `MinimumOSVersion` in the new device slice is `10.0`,
  well under the podspec's `16.4`.
- Simulator build green on both stub archs: 63 arm64 + 63 x86_64, 0 errors. The
  vendor dropped `requires objc` from the modulemap in this version; that does
  not break the stub. (Since 1.3.2 the two SDKs compile the same file count, so
  the count no longer distinguishes them — the link check above does.)
- Bridge contracts: veepoo-events, native-rejection and upstream-sdk coverage all
  pass. Lint, typecheck, build clean. JS suite: 900 tests, 60 suites, green.

## What is NOT verified — and what this does not fix

**No band was on the bench.** The daily-read state machine, connect +
password-verify callback ordering and the ECG `filterSignals`/`originalSignals`
population are all tuned against 2.2.88.15's exact runtime behaviour and none of
it is observable from a compile. A full hardware sync — connect, daily read to
100%, sleep + exercise + stored vitals, ECG with waveform, plus the
adopt-existing-link / daily-read watchdog / `BAND_BUSY_READING` paths — is still
outstanding before this pin ships to the app.

**No state-restoration API.** 2.2.101.15 still ships nothing for CoreBluetooth
restore identifiers. The only reconnection-adjacent additions are
`VPJH58ActiveMeasurementStateResume` (breakpoint-resume after reconnect) and the
power-off command. CB state restoration remains vendor-blocked.

## Bookkeeping

- `vendor-manifest.json`: `ios.veepooBleSdkVersion` 2.2.101.15,
  `iosBleSdk.lastReviewedHeadSha` a72fdefe, `updated` 2026-08-22.
- `vendor-sdk-snapshots/ios` re-fetched at the new SHA — that tree is
  gitignored, so it appears in no diff; `scripts/fetch-sdk-snapshots.sh`
  regenerates it from the `.fetch-sha` stamp on the next run.
- `package.json`, `ios/VeepooSDK.podspec`, `vendor-manifest.json`
  (`podspecModuleVersion`) and `module.json` → **1.3.3**. `module.json` had been
  left at 1.2.11 by 1.3.2's alignment pass; it is closed here.

Unrelated pre-existing breakage found while running the gates and left alone:
`scripts/ci-local.sh` invokes `build/bridge-contract/cli-check-*.js`, which no
longer exist (they are now `run-contract-checks.js <name>`), so the script fails
on a clean checkout of `main` too.
