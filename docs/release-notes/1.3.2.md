# 1.3.2 — vendor frameworks repackaged as XCFrameworks with stub simulator slices

## Why

A simulator build was a false BUILD. The podspec made it green by *not compiling
our code*:

```ruby
'EXCLUDED_SOURCE_FILE_NAMES[sdk=iphonesimulator*]' => 'VeepooSDK.swift VeepooSDKModule+*.swift'
```

The vendor frameworks are device-only, so on the simulator we dropped ~50 of the
53 files in `ios/VeepooSDK/`. A syntax error, a wrong API or a broken
`#if !targetEnvironment(simulator)` branch could only ever surface on a device
build. Demonstrated rather than assumed: appending `this is not valid swift @@@ %%`
to `VeepooSDKModule+ReadHelpers.swift` gave **BUILD SUCCEEDED, 0 errors** on
`-sdk iphonesimulator` and **11 errors** on `-sdk iphoneos`.

## What changed

**Packaging.** Each of the six vendored frameworks is now an `.xcframework` with
two slices: our real, unchanged device binary, and an empty `veepoo_stub()`
simulator slice that reuses the **real** `Headers/` and `module.modulemap`. The
vendor publishes no simulator slice at any version (checked
`HBandSDK/iOS_Ble_SDK`), so a stub is the only mechanism. Regenerate with
`scripts/build-xcframeworks.sh`.

`EXCLUDED_SOURCE_FILE_NAMES` is deleted and all 53 Swift files now compile on the
simulator.

**Bundled binaries are unchanged.** All six device slices are byte-identical to
1.3.1's — `veepooBleSdkVersion` is still `2.2.88.15`. This is a repackaging, not
a vendor bump. The plain `.framework` directories were replaced rather than kept
alongside, so the device slice is the single source of truth; git records the
moves as renames.

**Embedding moved to CocoaPods.** Declaring `vendored_frameworks` hands CocoaPods
the slice selection, the search paths, the `-framework` flags and the embed of
the four dynamic frameworks via `[CP] Embed Pods Frameworks`. The podspec's
manual `pod_target_xcconfig`/`user_target_xcconfig` and the config plugin's
`withVeepooFrameworkEmbed` run-script phase are therefore **removed**. Consumers
need no change; a non-clean prebuild may retain the old, now-inert phase.

**Simulator behaviour is honest again.** Compiling the real files woke 79
`#if targetEnvironment(simulator)` branches that had never run, because
`VeepooSDKSimulator.swift` (now deleted — it declared a second
`VeepooSDKModule`) had been the entire simulator surface. Two defects came with
them and are fixed:

- `readDeviceAllData` never settled its promise (whole body device-only, no
  `#else`), so a JS `await` hung forever.
- 27 handlers answered with fabricated data — `readBattery` reported 88%,
  `isBluetoothEnabled` returned `true`, `requestPermissions` returned
  `granted: true` on a machine with no Bluetooth radio.

They now reject `CAPABILITY_UNSUPPORTED`, following the vendor's own convention:
absence is a distinct state (`VPDeviceBloodGlucoseTestStateUnsupported`,
`VPTemperatureTestStateUnsupported`, …), and where an interface has no support
flag their iOS doc says "If a failed callback is triggered, it means that the
device does not support this interface."

`connect`, `disconnect` and `verifyPassword` deliberately keep their
fake-connected-band arms, so band UI can be developed without hardware — they
report a *session*, not a measurement.

## Scope of the guarantee

Simulator builds now catch **syntax** errors everywhere and **type** errors only
*outside* the `#if !targetEnvironment(simulator)` guards — Swift parses but does
not type-check an inactive branch. Vendor signature drift remains device-only:
verify with `-sdk iphoneos`.

Device builds were verified as compile + link (the `.app` embeds arm64 vendor
binaries at their real sizes). Band-on-hardware behaviour is unchanged by this
release — every source edit is inside a simulator-only branch or in packaging.

## Version alignment

`package.json`, `ios/VeepooSDK.podspec` and `vendor-manifest.json`
(`podspecModuleVersion`) had drifted to 1.3.0 / 1.2.11 / 1.2.11 respectively
while release notes had reached 1.3.1. All four now read **1.3.2**.

## Upstream

`gaozh1024/expo-veepoo-sdk` `b0e6d71` performed a similar migration but converted
only 2 of 6 frameworks and **kept** `EXCLUDED_SOURCE_FILE_NAMES`, so upstream
simulator builds still do not compile their own Swift. The technique was taken;
their binaries were not (their `VeepooBleSDK` is an older build — 1,464 ObjC
classes to our 1,694, missing `VPGSRResultModel`, `VPHRVTestManager` and the
manual blood/oxygen/temperature models).
